# RaceProof: where the idea came from

Checked October 28, 2026. Every link below was opened and read; the notes say what each source contributes and what the project takes from it. The two course documents (Project Details.pdf and OS_Project_Top5_Explained.pdf) are not repeated here.

**Origin in one paragraph.** RaceProof is not the name of an existing paper or system. The idea is assembled from three documented Linux mechanisms (memory-backed files with sealing, execution through a file descriptor, and the kernel's executable-memfd policy), applied to a classical security problem (time-of-check-to-time-of-use races on files), in a setting that recent work has started to care about (an AI agent or automated defender launching tools). The sealed-copy mechanism itself is prior art: runc has used exactly "copy into memfd, seal, execute" since its 2019 container-breakout fix. What the project adds is a controlled comparison of three launch policies for an agent tool launcher, measuring mismatches, correct launches, launch latency and memory. We have not found a published version of that comparison, but we also have not proven it does not exist.

## A. The mechanisms the broker uses

| Source | What it says | What we take from it |
| --- | --- | --- |
| [memfd_create(2), Linux man-pages](https://man7.org/linux/man-pages/man2/memfd_create.2.html) | Creates an anonymous, memory-backed file (Linux 3.17). With MFD_ALLOW_SEALING the file can be sealed; the stated purpose of sealing is to let a process rely on a peer being unable to change shared memory, instead of copying data before use to avoid races. | The sealed-copy policy: a private copy of the approved bytes. |
| [F_ADD_SEALS / F_GET_SEALS (fcntl), Linux man-pages](https://man7.org/linux/man-pages/man2/F_ADD_SEALS.2const.html) | Defines the seals. F_SEAL_WRITE blocks content changes, F_SEAL_SHRINK and F_SEAL_GROW block resizing, F_SEAL_SEAL locks the seal set, F_SEAL_FUTURE_WRITE (Linux 5.1) and F_SEAL_EXEC (Linux 6.3) are newer. | The exact seal set to apply after copying and before hashing. |
| [execveat(2), Linux man-pages](https://man7.org/linux/man-pages/man2/execveat.2.html) | Executes a program given a directory descriptor and pathname, or with AT_EMPTY_PATH the file referred to by the descriptor itself. | How both the descriptor policy and the sealed-copy policy launch: the exact file object that was hashed. |
| [fexecve(3), Linux man-pages, NOTES section](https://man7.org/linux/man-pages/man3/fexecve.3.html) | States the use case directly: verify (checksum) an executable before executing it. Hashing then execve by pathname is unsafe because the path can be swapped. Executing through the descriptor avoids the pathname race but "does not mitigate the problem that the contents of a file could be changed" between checksum and exec. | The clearest statement of the research gap. It predicts our expected result: the descriptor policy stops replacement but not in-place modification. Worth showing the professor. |
| [Executable and non-executable memfds, Linux kernel documentation](https://docs.kernel.org/userspace-api/mfd_noexec.html) | Introduces MFD_EXEC, MFD_NOEXEC_SEAL and the per-PID-namespace sysctl vm.memfd_noexec (values 0, 1, 2; most restrictive setting in the namespace hierarchy wins). Names runc as a legitimate user that copies a binary into a memfd, seals it and executes it. | The feasibility check we must do in week one, and the reason we record the kernel's policy and never weaken the host. |

## B. Prior art for the sealed-copy mechanism

| Source | What it says | What we take from it |
| --- | --- | --- |
| [runc commit 0a8e4117: "nsenter: clone /proc/self/exe to avoid exposing host binary to container"](https://github.com/opencontainers/runc/commit/0a8e4117e7f715d5fbeef398405813ce8e88558b) (Aleksa Sarai, co-developed by Christian Brauner, 2019) | Copies the runc binary into a memfd, seals it with F_SEAL_SEAL, F_SEAL_SHRINK, F_SEAL_GROW and F_SEAL_WRITE, checks the seals with F_GET_SEALS, and re-executes the copy with fexecve. Notes the cost: the binary loses page-cache sharing. | The sealed-copy policy is this design, applied to a tool launcher instead of runc itself. We must cite it as the direct precedent, not claim the mechanism. |
| [CVE-2019-5736: runc container breakout, LWN.net, February 2019](https://lwn.net/Articles/779542/) | Explains the vulnerability (a container overwriting the host runc binary through /proc/self/exe) and the memfd-based fix, including the sealing and the page-cache trade-off. | Background for the viva: why a real system paid the copy cost. |
| [Sealed files, LWN.net, Jonathan Corbet, April 2014](https://lwn.net/Articles/593918/) | Introduces file sealing and memfd_create as proposed by David Herrmann: with SEAL_SHRINK, SEAL_GROW and SEAL_WRITE set, the file becomes immutable. | History of the mechanism; sealing was designed for exactly the "peer must not change the bytes" problem. |

## C. The TOCTOU problem in the literature

| Source | What it says | What we take from it |
| --- | --- | --- |
| [CWE-367: Time-of-check Time-of-use (TOCTOU) Race Condition, MITRE](https://cwe.mitre.org/data/definitions/367.html) | Formal definition: a resource's state changes between the check and the use in a way that invalidates the check. Its example is access() followed by fopen(), both operating on file names rather than file handles. | The vocabulary for the research question and the class of weakness we measure. |
| [Bishop and Dilger, "Checking for Race Conditions in File Accesses", Computing Systems 9(2), 1996](https://static.usenix.org/publications/compsystems/1996/spr_bishop.pdf) | Early formal treatment of TOCTTOU binding flaws in UNIX, with a semantic method for detecting them. | Shows the problem is three decades old and still unsolved at the pathname level. |
| [Dean and Hu, "Fixing Races for Fun and Profit: How to Use access(2)", USENIX Security 2004](https://www.usenix.org/conference/13th-usenix-security-symposium/fixing-races-fun-and-profit-how-use-access2) | Argues no portable deterministic fix exists without changing the system-call interface; proposes a probabilistic defense; shows faster CPUs make the attack easier. | Why we test under CPU load and report rates with trial counts rather than claiming a proof. |
| [Borisov, Johnson, Sastry and Wagner, "Fixing Races for Fun and Profit: How to Abuse atime", USENIX Security 2005](https://www.usenix.org/legacy/events/sec05/tech/full_papers/borisov/borisov_html/index.html) | Breaks the probabilistic defense with "filesystem mazes", winning the race over 90% of the time. | Motivates deterministic, barrier-controlled interleavings in the harness: an attacker can be made reliable, so a policy must hold even then. |
| [Wei and Pu, "TOCTTOU Vulnerabilities in UNIX-Style File Systems: An Anatomical Study", FAST 2005](https://static.usenix.org/event/fast05/tech/full_papers/wei/wei.pdf) | Models TOCTTOU in Unix file systems and enumerates 224 vulnerable system-call pairs; demonstrates exploits against rpm and vi. | The check-then-execute pair we study is one instance of this enumeration. |
| [Tsafrir, Hertz, Wagner and Da Silva, "Portably Solving File TOCTTOU Races with Hardness Amplification", FAST 2008 (Best Paper)](https://static.usenix.org/events/fast08/tech/tsafrir.html) | A user-level defense that survives mazes without kernel changes. | The strongest prior user-level answer; our approach instead uses kernel primitives (descriptors, seals) and measures their cost. |

## D. Related kernel integrity mechanisms (contrast, not used)

| Source | What it says | Why it is not our approach |
| --- | --- | --- |
| [IMA policy ABI, Linux kernel (Documentation/ABI/testing/ima_policy)](https://kernelsources.org/source/xref/linux/Documentation/ABI/testing/ima_policy) | The Integrity Measurement Architecture can measure and appraise every executable at exec time (BPRM_CHECK), against hashes or signatures. | A system-wide, root-configured kernel policy. Our broker is an unprivileged user-space design an agent can adopt without reconfiguring the host. |
| [fs-verity, Linux kernel documentation](https://docs.kernel.org/filesystems/fsverity.html) | Builds a Merkle tree over a read-only file so every read is verified; IMA can appraise executables by their fs-verity digest. | Requires filesystem support and a read-only file set up in advance; it protects the file, while our sealed copy protects the launch. A natural comparison point for the report's discussion. |

## E. The AI-agent setting (closest recent work)

| Source | What it says | How we differ |
| --- | --- | --- |
| [Lilienthal and Hong, "Mind the Gap: Time-of-Check to Time-of-Use Vulnerabilities in LLM-Enabled Agents", arXiv 2508.17155, August 2025](https://arxiv.org/abs/2508.17155) | Defines TOCTOU for agents as validating external state (a file or an API response) that changes before use; introduces TOCTOU-Bench (66 tasks); evaluates prompt rewriting, state-integrity monitoring and tool-fusing. | They work at the agent-plan level and measure attack windows in tasks. We work at the OS launch boundary with kernel primitives and measure whether the executed bytes match the approved bytes. |
| [Weng, "What You Approve Is What Executes: Consent Integrity for Black-Box LLM Agents", arXiv 2606.02668, June 2026](https://arxiv.org/abs/2606.02668) | Argues an agent's approval dialog must be derived from, and bound to, the real low-level action that executes, since a compromised agent can describe one action and run another. | Same spirit (approve-then-execute integrity) one layer up. Our broker is a concrete way to bind "approved" to "executed" for a native binary. Both are preprints, not peer-reviewed versions. |

## E2. Closest public implementations and preprints (found October 28, 2026)

These are the nearest things to RaceProof in the wild. None is a peer-reviewed measurement study; three are code, two are preprints. They matter because they show the copy-seal-execute pattern is already being applied to agent tool runners.

| Source | What it does | How we differ |
| --- | --- | --- |
| [Wang and Zheng, "Sandlock: Confining AI Agent Code with Unprivileged Linux Primitives", arXiv 2605.26298, May 2026](https://arxiv.org/abs/2605.26298) | An unprivileged sandbox for agent code (Landlock rules plus a small supervisor). Its TOCTOU section freezes every task that could alias the child's address space before reading execve arguments, so the inspected argv cannot change. | It protects the arguments of execve, not the bytes of the file being executed. It does not mention memfd, sealing or exec through a held descriptor. Complementary, not overlapping. |
| [VirusTotal MCP, execution-control documentation (docs/control.md)](https://github.com/VirusTotal/virustotal-mcp/blob/main/docs/control.md) | A runner for one exact command form (python3 -I script.py). It opens the script once, copies at most 8 MiB, checks size and modification metadata, seals the copy, computes SHA-256 from the sealed copy, checks it against VirusTotal and a local policy, then hands those same bytes to Python as non-executable data. States it does not claim protection against other processes running as the same user. | Same sequence as our sealed-copy policy, applied to scripts handed to an interpreter rather than ELF executed with execveat. No measurement of mismatch rate or overhead, and no racing attacker in its evaluation. |
| [WORKSPACE-GUARD, Independent-AI-Labs (README)](https://github.com/Independent-AI-Labs/WORKSPACE-GUARD) | A shell guard that scans untrusted scripts against a pattern table and "executes the exact scanned bytes via a sealed memfd, closing the scan-then-exec TOCTOU race"; trusted scripts run by path after provenance validation. | Public implementation evidence of the mechanism for scripts. No published measurements. |
| [control-stack PR 23: opt-in sealed memfd script loading (merged October 9, 2026)](https://github.com/jwcodes12/control-stack/pull/23) | Hashes and checks a script, places the bytes in a sealed memfd and runs them through /proc/self/fd/N; fails closed when seals are unsupported. | Same pattern again for scripts; confirms practitioners are converging on it. |
| [.CMPCT draft PR 379: kernel-sealed memfd source ownership test](https://github.com/FCMO-AI/.CMPCT/pull/379) | Tests whether a write-sealed memfd copy gives a stable source; reports same-user writes denied with EPERM. States plainly: "Sealed clone does not supply an atomic snapshot while the original is copied." | Names the exact gap our harness targets: a modification that lands during the copy. Measuring how often that produces a torn copy, and whether hash-after-seal catches it, is open. |

## F. What is established and what the project adds

- Established, and to be cited rather than claimed: TOCTOU on files (C), descriptor-based execution and its limit (fexecve NOTES), file sealing and memfd (A), the copy-seal-execute pattern (runc, B), and its application to agent tool runners for scripts (E2: VirusTotal MCP, WORKSPACE-GUARD, control-stack).
- Added by this project: a controlled measurement, which none of the above provides. Three interchangeable launch policies in one broker; a reproducible race harness with barrier-controlled and uncontrolled interleavings, including a modification that lands during the copy; and measured check/use mismatch, correct-launch, rejection and error rates against launch latency, bytes copied and peak memory, across replacement and in-place modification. The result tells implementers like those in E2 what their design choice buys and costs.
- Not established: that this comparison is previously unpublished. No source found makes it, but absence of evidence is not proof; the class register and a fresh literature check before the report are still required. The proposal should describe itself as a measurement study of an established mechanism, not as a new technique.
